## 二、后端技术栈

### 2.1 核心框架

| 技术 | 版本 | 用途 | 选型理由 |
|------|------|------|---------|
| **Python** | 3.13 | 编程语言 | 与现有分析引擎同语言，直接复用 `review-analyzer-skill/src/` 全部模块 |
| **FastAPI** | ≥0.115 | Web 框架 | 异步原生支持（SSE 推送）；自动生成 OpenAPI 文档；Pydantic v2 深度集成；性能接近 Node.js |
| **Uvicorn** | ≥0.32 | ASGI 服务器 | Python 异步标准服务器，FastAPI 官方推荐 |
| **Gunicorn** | ≥23.0 | 进程管理 | 多 worker 模式跑 Uvicorn，生产级并发处理 |

**为什么是 FastAPI 而非 Django？**

| 维度 | FastAPI | Django + DRF |
|------|---------|--------------|
| 异步支持 | ✅ 原生 async/await | ⚠️ 3.1+ 才开始支持，生态滞后 |
| API 文档 | ✅ 自动生成 Swagger + ReDoc | ⚠️ 需要 drf-spectacular 等插件 |
| 数据校验 | ✅ Pydantic v2 (Rust 内核，极快) | ⚠️ DRF Serializer (纯 Python) |
| SSE | ✅ 原生 `StreamingResponse` | ⚠️ 需要额外配置 |
| 体积 | 轻量，按需安装 | 笨重，自带 ORM/Admin/Template |
| 学习曲线 | 低，Flask-like 直觉 | 高，概念多（app/model/view/serializer） |
| 适合场景 | **API 服务 + 前后端分离** | 全栈单体应用 |

**结论**：本项目是标准的「前后端分离 + API 驱动」架构，FastAPI 是最优解。Django 的 ORM Admin / Template 等能力在本项目中完全用不上。

### 2.2 数据校验

| 技术 | 用途 | 理由 |
|------|------|------|
| **Pydantic v2** | 请求/响应/配置校验 | FastAPI 内置；Rust 内核性能极快；支持嵌套模型、validator、JSON Schema 导出 |

```python
# schemas/task.py — Pydantic v2 示例
from pydantic import BaseModel, Field, field_validator
import re

class TaskCreate(BaseModel):
    asin: str = Field(min_length=10, max_length=10, description="Amazon 商品 ASIN")
    site: Literal["US", "UK", "DE", "JP"] = Field(default="US")
    max_reviews: int = Field(default=500, ge=10, le=2000)

    @field_validator("asin")
    @classmethod
    def validate_asin(cls, v: str) -> str:
        if not re.match(r"^[A-Z0-9]{10}$", v.upper()):
            raise ValueError(f"无效的 ASIN: {v}")
        return v.upper()
```

### 2.3 ORM & 数据库迁移

| 技术 | 版本 | 用途 | 理由 |
|------|------|------|------|
| **SQLAlchemy** | ≥2.0.36 | ORM | Python 生态标准，2.0 原生支持 async/await，与 FastAPI 配合最佳 |
| **asyncpg** | ≥0.30 | PostgreSQL 异步驱动 | 最快的 Python PostgreSQL 驱动，重新实现了 PostgreSQL 协议 |
| **Alembic** | ≥1.14 | Schema 迁移 | SQLAlchemy 官方迁移工具，自动生成迁移脚本，支持 `upgrade` / `downgrade` |

**SQLAlchemy 2.0 async 模式最佳实践**：

```python
# core/database.py
from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession, async_sessionmaker

engine = create_async_engine(
    settings.DATABASE_URL,      # postgresql+asyncpg://...
    echo=False,
    pool_size=20,
    max_overflow=10,
    pool_pre_ping=True,         # 连接前检测有效性
)

async_session = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    """FastAPI 依赖注入：每个请求一个数据库会话"""
    async with async_session() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
```

**为什么用 `expire_on_commit=False`？**
避免在 commit 后访问懒加载属性时触发隐式查询（常见的 N+1 问题来源）。

### 2.4 异步任务

| 技术 | 版本 | 用途 | 理由 |
|------|------|------|------|
| **Celery** | ≥5.4 | 异步任务队列 | Python 标准方案；任务生命周期管理（重试/超时/优先/撤销）；成熟的监控工具 Flower |
| **Redis** | 7 | Broker + Result Backend | 高性能内存数据库；同时充当 Celery 消息中间件和结果存储 |
| **redis-py** | ≥5.2 | Python Redis 客户端 | Celery 官方推荐的 Redis driver |

**Celery 配置要点**：

```python
# tasks/celery_app.py
from celery import Celery

celery_app = Celery(
    "review_analyzer",
    broker=settings.CELERY_BROKER_URL,      # redis://redis:6379/0
    backend=settings.CELERY_RESULT_BACKEND, # redis://redis:6379/0
)

celery_app.conf.update(
    task_serializer="json",
    result_serializer="json",
    accept_content=["json"],
    timezone="Asia/Shanghai",
    enable_utc=True,
    task_track_started=True,
    task_acks_late=True,              # 任务完成后才 ACK（防止 worker 崩溃丢任务）
    task_reject_on_worker_lost=True,  # worker 丢失时重新入队
    task_soft_time_limit=900,         # 软超时 15min（抛出异常，可捕获清理）
    task_time_limit=1200,             # 硬超时 20min（强制 kill）
    worker_prefetch_multiplier=1,     # 每个 worker 一次只取一个任务（长任务场景）
    task_default_retry_delay=60,      # 失败后 60s 重试
    task_max_retries=3,               # 最多重试 3 次
)
```

**为什么 `worker_prefetch_multiplier=1`？**
分析任务耗时 5-15 分钟且不均衡。如果预取了 4 个任务（默认），一个 worker 可能积压 3 个长任务而另一个空闲。设为 1 确保公平分发。

### 2.5 AI 引擎集成

| 技术 | 用途 | 理由 |
|------|------|------|
| **Claude Code CLI** (`claude --print`) | AI 推理（22 维打标 + 报告生成） | 零 API Key 成本；复用用户 Claude 订阅配额；prompt 不受 API context window 限制 |
| **subprocess** | 调用 CLI | Python 标准库，无需额外依赖 |

```python
# 统一入口（复用现有 config.py）
from src.config import config

def call_claude(prompt: str, timeout: int = 600) -> str:
    """调用 Claude Code CLI 执行推理

    Args:
        prompt: 完整的 prompt 文本（含指令和评论数据）
        timeout: 超时时间（秒）

    Returns:
        CLI 的 stdout 输出

    Raises:
        RuntimeError: CLI 不可用或执行失败
    """
    cmd = config.build_cli_cmd(prompt)  # 自动解析 claude vs opencode
    result = subprocess.run(
        cmd,
        capture_output=True,
        text=True,
        timeout=timeout,
    )
    if result.returncode != 0:
        raise RuntimeError(f"CLI 执行失败: {result.stderr[:500]}")
    return result.stdout
```

## 四、数据层技术栈

### 4.1 主数据库 — PostgreSQL 16

| 能力 | 用途 | 本项目如何使用 |
|------|------|--------------|
| **JSONB** | 半结构化数据存储 | 标签数据 (`tags`)、配置快照 (`config`)、统计数据 (`stats`) |
| **GIN 索引** | JSONB 高效查询 | `idx_tagged_tags ON tagged_reviews USING GIN (tags)` |
| **全文搜索** | 评论内容检索 (后续) | `tsvector` + `tsquery` |
| **窗口函数** | 统计分析 | 情感分布、评分趋势 |
| **CTE** | 复杂查询 | 多表关联聚合 |
| **事务** | 数据一致性 | 任务创建 → 评论批量插入 |

**为什么不用 MongoDB？**
- JSONB 已覆盖灵活 schema 需求，tag 结构虽灵活但关系固定（review → tags）
- 评论-打标-画像-报告之间有强外键约束，SQL 保证引用完整性
- 后续可能需要全文搜索、聚合分析，PostgreSQL 原生支持

### 4.2 缓存 & 消息队列 — Redis 7

| 用途 | 场景 |
|------|------|
| **Celery Broker** | 分析任务消息传递 |
| **Celery Result Backend** | 任务结果存储 + 状态查询 |
| **SSE 状态缓存** (可选) | 缓存当前进度避免重复查询数据库 |
| **API 限流** (后续) | 配合 slowapi 做 per-IP 速率限制 |

### 4.3 文件存储 — MinIO

| 用途 | 场景 |
|------|------|
| **CSV 上传文件** | 用户上传的评论 CSV |
| **分析产物** | HTML 看板、Markdown 报告、打标 CSV |
| **导出物缓存** | 下载请求直接从 MinIO 取，不重复生成 |

**为什么用 MinIO 而非本地文件系统？**
- S3 API 兼容，后续切换到 AWS S3 无需改代码
- Docker 单容器部署，零运维成本
- 自带 Web Console（端口 9001），便于调试
- 文件持久化通过 Docker volume，不依赖容器生命周期

**MinIO 初始化脚本**：

```python
# core/minio.py
from minio import Minio

def ensure_bucket():
    client = Minio(
        settings.MINIO_ENDPOINT,
        access_key=settings.MINIO_ACCESS_KEY,
        secret_key=settings.MINIO_SECRET_KEY,
        secure=False,  # 内网通信不加密
    )
    if not client.bucket_exists(settings.MINIO_BUCKET):
        client.make_bucket(settings.MINIO_BUCKET)
    return client
```

## 六、架构决策记录 (ADR)

### ADR-001: FastAPI vs Django vs Flask

- **决策**：FastAPI
- **理由**：
  - 本项目是 API-first 架构，不需要 Django 的全栈能力（ORM Admin、Template Engine）
  - 异步原生支持对 SSE 实时推送至关重要
  - Pydantic v2 的 Rust 内核比 DRF Serializer 快 10x+
  - 自动生成 Swagger 文档，降低前后端协作成本
  - 学习曲线低，新贡献者上手快

### ADR-002: PostgreSQL JSONB vs MongoDB

- **决策**：PostgreSQL 16 JSONB
- **理由**：
  - 数据间存在强关系（任务→评论→打标→画像→报告），外键约束保证完整性
  - JSONB + GIN 索引已满足灵活 schema 需求（22 维标签可能扩展）
  - 减少运维复杂度：少维护一个 MongoDB 容器
  - PostgreSQL 的全文搜索可覆盖后续评论检索需求

### ADR-003: Celery vs 纯后台线程

- **决策**：Celery + Redis
- **理由**：
  - 分析任务耗时 5-15 分钟，必须与 HTTP 请求生命周期解耦
  - Celery 提供重试机制（3 次）、超时控制、任务状态追踪
  - Worker 可独立扩容，不影响 API 服务
  - Redis 同时充当 Broker 和缓存，复用基础设施

### ADR-004: Next.js vs Vite SPA

- **决策**：Next.js 15 (SPA 模式为主)
- **理由**：
  - 分享链接功能需要 SSR 渲染 OG 标签（后续阶段）
  - Next.js 支持同一项目中按页面选择性 SSR，避免后期迁移成本
  - `next/image` 内置图片优化（评论图片展示）
  - Docker 部署 `next start` 已成熟

### ADR-005: Zustand + TanStack Query vs Redux Toolkit

- **决策**：Zustand + TanStack Query
- **理由**：
  - 本项目状态复杂度中等偏低，不需要 Redux 的 action/reducer/slice 分层
  - Zustand ~1KB，API 极简；配合 TanStack Query 覆盖服务端缓存
  - 新贡献者 10 分钟可理解，降低开源项目门槛
  - 职责明确：Zustand 管 UI，TanStack Query 管服务端数据

### ADR-006: Claude CLI subprocess vs Anthropic API

- **决策**：Claude Code CLI subprocess（默认），预留 API 扩展点
- **理由**：
  - 零 API Key 成本：利用用户已有 Claude Code 订阅配额
  - 零配置：`claude` CLI 已安装即可
  - Prompt 长度不受 API context window 限制（22 维标签需长 prompt）
  - 长期可通过配置 `CLI_ENGINE=api` 切换到 API 模式

### ADR-007: structlog vs Python logging

- **决策**：structlog
- **理由**：
  - 输出 JSON 行，`docker logs` 直接解析，无需额外日志服务
  - 支持上下文绑定（`logger.bind(task_id=...)`），减少重复代码
  - 零外部依赖，与 Docker Compose 一键启动理念一致
  - Sentry / ELK 等集中式日志系统可通过 hook 按需添加

### ADR-008: uv + pnpm vs pip + npm

- **决策**：uv (Python) + pnpm (Node.js)
- **理由**：
  - 前后端包管理理念统一（快 + 严格隔离 + lock 文件）
  - `uv` 比 pip 快 10-100x，`pnpm` 比 npm 省 50%+ 磁盘
  - 严格的依赖隔离避免"本地能跑 CI 报错"的幽灵依赖问题
